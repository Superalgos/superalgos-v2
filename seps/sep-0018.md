# SEP-18: Signal tracing and logs

- Status: Draft
- Criteria: 0/8 done

## Motivation

A signal passes through four parties before it becomes an order: the strategy that decided it, the provider bot that
signed and published it, the relay that timed its release per tier, and the follower bot that verified and executed
it. When a follower says "I never got that signal" or "it executed late", today the answer is spread across separate
logs with no common key. This SEP makes every step of a signal's life a structured log record keyed by the signal's
event id, so one command can show the whole path, from the bar the strategy decided on to the fill, and say where it
stopped and why.

## Design

- **One key.** Every record about a signal carries `signal_id` (the Nostr event id) plus `provider` (pubkey) and
  `seq`. Records about a follower's handling also carry `follower` (its device pubkey).
- **One shape.** Records are JSON lines: `ts` (UTC, ms), `component` (`strategy`, `provider`, `relay`, `follower`),
  `stage`, `signal_id`, `provider`, `seq`, `outcome` (`ok` or a short reason code), plus stage fields. Python and Go
  emit the same field names.
- **Stages.** strategy: `decided` (bar, instrument, the conditions that fired). provider: `signed`, `anchored`,
  `published` (relay ack or refusal). relay: `received`, `stored`, `released` (per tier, scheduled and actual time),
  `refused` (reason). follower: `received`, `verified` or `rejected` (reason), `recorded_as_history`, `executed`,
  `filled`, `skipped` (risk limit, stale).
- **Reason codes, not prose.** Rejections and refusals use a fixed, documented set of codes (for example
  `bad_signature`, `expired_delegation`, `chain_gap`, `stale_bar`, `not_entitled`, `rate_limited`), each with a
  one-line human explanation in the docs.
- **Local by default.** Each party writes its own records on its own machine. Nothing is sent anywhere. `sa trace`
  merges the files a user has: their own, plus any a provider or follower chooses to share for debugging.

## Criteria

- [ ] SEP-18.1: The provider bot, the follower bot and the relay write one JSON-lines record for every stage listed in the design, each with `ts`, `component`, `stage`, `signal_id`, `provider`, `seq` and `outcome`, using the same field names in Python and Go.
  Probe: integration: one signal from provider to follower through a real relay. Pass: every listed stage present once per party (per tier for `released`), fields valid against one JSON Schema shared by both languages. Tool: pytest + go test + schema check.
- [ ] SEP-18.2: Every rejection, refusal or skip carries a reason code from a single documented list; an unknown code fails the build.
  Probe: test: the code list in the docs vs every code emitted in the codebase. Pass: sets equal; a test emitting an undeclared code fails. Tool: pytest + go test.
- [ ] SEP-18.3: `sa trace <signal_id>` merges the records it is given (own logs by default, plus files passed with `--include`) into one time-ordered path and states the last stage reached and, if the path stopped, the reason code and the party that stopped it.
  Probe: integration: four runs (delivered and filled; rejected for a chain gap; refused by the relay; follower joined late and recorded it as history). Pass: each run's output names the correct last stage, party and reason. Tool: pytest + sarelay.
- [ ] SEP-18.4: The strategy's `decided` record names the bar (open time, timeframe) and the conditions and values that fired, so a signal can be traced back to the market data that caused it.
  Probe: test: a backtest and a paper run on the same candles. Pass: the `decided` records match bar for bar, with the same conditions and values. Tool: pytest.
- [ ] SEP-18.5: The relay's `released` record per tier holds the scheduled and the actual release time, so an early or late release is visible from logs alone.
  Probe: test: tiered delivery to four tiers. Pass: one record per tier; actual is never before scheduled. Tool: go test.
- [ ] SEP-18.6: Anti: any log record contains a private key, a device or exchange secret, a passphrase, an exchange API key, or the plaintext of a private (NIP-44) signal.
  Probe: property: random signals, keys and configs through all components; scan every emitted record. Pass: no secret or plaintext of a private signal appears. Tool: hypothesis + go test.
- [ ] SEP-18.7: Logs stay on the machine that wrote them: no component sends log records over the network, and the relay's records about a client carry its pubkey, not its IP address, unless the operator turns IP logging on explicitly.
  Probe: test: run with a network capture and default config; then with IP logging on. Pass: no log traffic leaves the host; IP present only when enabled. Tool: pytest + go test.
- [ ] SEP-18.8: Log files rotate by size and age with documented defaults, so a long-running provider, follower or relay never fills its disk with logs.
  Probe: test: write past the size limit and past the age limit. Pass: old files rotated or removed; disk use stays under the configured cap. Tool: pytest + go test.
