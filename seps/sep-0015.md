# SEP-15: Explain and notify

- Status: Draft
- Criteria: 0/4 done

## Motivation

A user trusts a bot only when they can see why it acted or did not, and hear about it without watching a dashboard. Followers also need the rules they are subject to (tiers, delays, thresholds) stated plainly, and an honest record of which exchanges have actually been checked. This SEP covers that: a step-by-step explanation of strategy decisions on the chart, notifications from the user's own bot, a written statement of every access rule, and a dated exchange status list.

## Criteria

- [ ] SEP-15.1: Engine scrub: sliding along a backtest on the chart shows, for the selected bar, every stage, situation and condition of the strategy with its value and whether it fired, and the reason an expected order did not happen.
  Probe: test+browser: backtest with a known non-fire bar. Pass: node values and reason shown for that bar. Tool: bun test + Chrome.
- [ ] SEP-15.2: Notifications: a follower or provider bot sends Telegram messages (Discord next) for signal received, order placed or rejected, limit reached, bot stopped or erroring, and answers `/status`; the bot token lives only in the user's keystore.
  Probe: integration: Telegram test bot; keystore scan. Pass: messages for each event; `/status` answers; token not in plaintext. Tool: pytest + Telegram test chat.
- [ ] SEP-15.3: The user guide states every access rule a user meets: minimum power to register as provider, tier table and delays, per-provider private thresholds, allocation delay D, and what zero power gets.
  Probe: review: user guide vs relay config defaults. Pass: every rule present, values match. Tool: rg + review.
- [ ] SEP-15.4: A dated exchange status matrix in the repo lists, per venue, whether backtest, paper, testnet and live are verified, with the date and version of the last check; an entry older than 90 days shows as unverified.
  Probe: test: matrix file; entry dated > 90 days. Pass: rendered as unverified. Tool: pytest.
