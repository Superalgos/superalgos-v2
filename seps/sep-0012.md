# SEP-12: Guided install and setup (B2C)

- Status: Accepted
- Criteria: 5/23 done

## Motivation

v1 lost its users at install (32-bit Pi OS, Docker by hand, weekly `git pull`, node setup). v2 installs like a consumer app on a desktop (macOS, Linux, Windows) or as a container on a VPS or SBC, and a "next, next, next" wizard takes a non-technical user from wallet to running bot. Hosting is the user's concern; v2 ships the software only.

## Criteria

- [ ] SEP-12.1: Installers for macOS (arm64), Linux (x86_64, arm64) and Windows (x64) install the engine as a background service that starts at login or boot and opens the setup wizard in the browser, with no terminal step.
  Probe: ci: build and install each installer on a clean runner. Pass: service up, wizard URL answers. Tool: CI matrix (macos-14, ubuntu x64/arm64, windows).
- [ ] SEP-12.2: The setup wizard walks connect wallet (SIWE) → delegate device key (wallet signs) → add exchange → pick provider and budget → start on paper → go live, and resumes at the same step after the browser is closed.
  Probe: e2e+browser: walk all steps; close tab mid-way; reopen. Pass: same step restored; bot running on paper. Tool: pytest + browser (Chrome).
- [ ] SEP-12.3: An exchange API key entered in the wizard is checked against the exchange before it is accepted and is stored only in the encrypted keystore on the user's engine.
  Probe: test+integration: key check against mocked exchange; keystore file. Pass: accepted key encrypted on disk, absent from logs and API responses. Tool: pytest (+ live key: deferred).
- [ ] SEP-12.4: Anti: the wizard accepts an exchange API key with withdrawal permission enabled.
  Probe: property: random permission sets with withdrawals on. Pass: always rejected, error names the permission. Tool: hypothesis.
- [ ] SEP-12.5: Anti: live trading starts without an explicit confirmation on a screen that shows the budget, the provider and the key's permissions.
  Probe: test+browser: go-live request without confirmation token. Pass: refused. Tool: pytest + browser (Chrome).
- [ ] SEP-12.6: Anti: a client that is neither on loopback nor holding the one-time setup token or a paired-device credential reaches any setup or management endpoint.
  Probe: integration: every setup/management route from a non-loopback client without token. Pass: all 401. Tool: pytest.
- [ ] SEP-12.7: A container's first run serves the same wizard, locked by a one-time setup token printed to its log, so a VPS wizard is never open to the internet.
  Probe: e2e: `docker run` fresh volume; wizard without/with log token. Pass: 401 / 200. Tool: pytest + docker.
- [ ] SEP-12.8: On a desktop install the keystore's master secret lives in the OS secret store (macOS Keychain, Windows Credential Manager, Linux Secret Service) and no `master.secret` file is written.
  Probe: integration: wizard run on macOS, Windows, Linux runners. Pass: secret in OS store; no master.secret on disk. Tool: pytest + `keyring` CI matrix.
- [ ] SEP-12.9: Anti: any file the engine writes contains an exchange key, a device key or a passphrase in plaintext (scan of the whole data directory after a full wizard run).
  Probe: grep+test: scan data dir for key/passphrase bytes after wizard. Pass: 0 hits. Tool: pytest.
- [ ] SEP-12.10: On a headless install (container, SBC) the master secret comes from a platform secret (Docker/compose secret, systemd credential, TPM-sealed where available) or is typed into the wizard after boot; with none present the engine refuses to unlock and names the options.
  Probe: e2e: container with/without secret mount; wizard unlock. Pass: unlocks / refuses naming options. Tool: pytest + docker.
- [ ] SEP-12.11: The wizard warns, on the key step and the go-live confirmation, when the exchange key has no IP restriction, and shows the box's public IP to whitelist.
  Probe: test+browser: Binance reply with ipRestrict false / true. Pass: warning shown / absent. Tool: pytest + bun test.
- [ ] SEP-12.12: Optional: on a box with a TPM or YubiKey, the device key is generated and kept in the hardware and signs from there; the delegation format is unchanged.
  Probe: integration: device key on swtpm / YubiKey; sign + verify a signal. Pass: verifies; private key not exportable. Tool: pytest + swtpm.
- [x] SEP-12.13: The Providers and Provider pages update on their own: a new signal or record change appears within 20 s without a reload, polling pauses while the tab is hidden, and a background refresh never blanks the page or replaces shown data with an error. Evidence: `useApi` fake-timer tests; browser check against `sa demo` (a new signal appeared with no reload).
  Probe: test+browser: fake-timer tests on useApi (refetch, hidden-tab pause, stale-on-error); real Chrome on the live stack. Pass: new signal shown ≤ 20 s, no reload. Tool: bun test + browser (Chrome).
- [x] SEP-12.14: Each signal on the Provider page shows one plain status for the provider ("out": signed, time-stamped, on the relay; or which step is missing), with no other follower's data on that page. Evidence: browser check against `sa demo` (Provider page signals table shows "Out", no follower data); pytest and bun tests.
  Probe: test+browser: provider page per-signal status from relay + anchor data. Pass: "out" or the missing step; no follower rows. Tool: bun test + pytest + Chrome.
- [x] SEP-12.15: A follower sees its own signals (received at, its tier's scheduled delay, executed or rejected with the reason), read only from its own ledger; the page lists no other follower. Evidence: browser check (My power, My signals rows); `/api/me/signals` reads the follower's own ledger only; pytest covers another wallet returning empty.
  Probe: test+browser: follower view from `me_home` ledger. Pass: own receipts only, with delay and execution result. Tool: pytest + bun test + Chrome.
- [x] SEP-12.16: The per-tier delivery timeline appears only when the API runs with dev views on (`sa demo` on, a production deployment off); with them off no page or API response exposes it. Evidence: `sa demo` shows the Dev views nav; pytest: route returns 404 and no receipts with dev views off; A test asserts the live API config leaves them off.
  Probe: test: API with dev views off vs on. Pass: timeline route + data absent when off. Tool: pytest + bun test.
- [x] SEP-12.17: The provider chart extends to the current time and refreshes with the page, and every time shown is in the viewer's local zone with its UTC offset labelled. Evidence: browser check against a live stack (last candle is the current 15m bar, axis caption shows local time and UTC offset); fake-clock bun tests; open tabs reload once on a new build.
  Probe: test+browser: chart window end vs now; tz rendering. Pass: last candle within one bar of now; local time + offset. Tool: bun test + Chrome.
- [ ] SEP-12.18: A public test relay answers at a project-controlled `wss://` hostname with a valid certificate, deployed to the project's test host by the repo's CI from a commit on `main`; the relay listens only behind the TLS proxy.
  Probe: Holds when SEP-12.19 to SEP-12.19 all hold.
- [ ] SEP-12.19: The relay ships as its own arm64 image holding only the `sarelay` binary and its config (no Python, no engine), under 100 MB; the test host runs that image, never the full `superalgos-v2` image (over 2 GB).
  Probe: build+inspect: `docker buildx build --platform linux/arm64` of the relay image; `docker image inspect` on the test host. Pass: size < 100 MB; no python in the image; the test host container uses it. Tool: docker + ssh.
- [ ] SEP-12.20: A tester with only Docker follows Atlas and Vega on the test relay from the one-page guide (`docs/testers.md`) and sees, per signal: received, verified, executed on paper.
  Probe: e2e: fresh machine, guide only. Pass: follower logs received/verified/executed for a live signal. Tool: tester run + log.
- [ ] SEP-12.21: The project's demo providers publish to the test relay with their existing keys, and their bundle (history from before the move included) still verifies and scores.
  Probe: integration: `sa provider export` + `sa verify`/`sa record` after the move. Pass: verifies; seq chain unbroken across relays. Tool: pytest + CLI.
- [ ] SEP-12.22: Production uses `superalgos.org` (relay and dashboard); the test relay hostname appears in no production default.
  Probe: grep: defaults in code, compose, docs. Pass: 0 hits for the test relay hostname outside test docs/config. Tool: rg.
- [ ] SEP-12.23: An exchange key can instead be a 1Password reference (`op://vault/item/field`) read at use time through a 1Password service account, never copied to disk.
  Probe: test: `op://` reference with fake `op` client. Pass: key read in memory only; 0 bytes on disk. Tool: pytest.
