# SEP-3: Verifiable signals

- Status: Accepted
- Criteria: 37/46 done

## Motivation

The reason SA exists; a track record anyone can recompute is what Telegram signal groups cannot offer.

## Criteria

- [x] SEP-3.1: A versioned signal schema exists.
  Probe: Holds when SEP-3.2 to SEP-3.3 all hold.
- [x] SEP-3.2: The Pydantic signal model rejects a signal missing any of: instrument, side, action, size fraction, provider identity, timestamp, signature.
  Probe: property: signal missing a required field. Pass: rejected. Tool: hypothesis.
- [x] SEP-3.3: Serialising then parsing any valid signal returns an equal object (property test).
  Probe: property: serialise → parse. Pass: equal object. Tool: hypothesis.
- [x] SEP-3.4: A signal whose payload is altered after signing fails verification (property test over random payload mutations).
  Probe: property: mutated payload. Pass: always fails verify. Tool: hypothesis.
- [x] SEP-3.5: A provider's strategy running in Nautilus emits a signal on every order intent without code changes to the strategy.
  Probe: integration: Nautilus strategy emits signals. Pass: 1 signal per order intent. Tool: pytest.
- [ ] SEP-3.6: A signal published by a provider reaches a subscribed follower in under 5 seconds on the reference transport.
  Probe: integration: publish → receive latency. Pass: < 5 s p95. Tool: pytest timing.
- [ ] SEP-3.7: Anyone can recompute a provider's track record from the signed history plus public candle data.
  Probe: Holds when SEP-3.8 to SEP-3.11 all hold.
- [x] SEP-3.8: The tool's PnL for a fixture history matches a hand-computed expected value.
  Probe: test: PnL on fixture history. Pass: = expected. Tool: pytest.
- [x] SEP-3.9: The tool's win rate for a fixture history matches the expected value.
  Probe: test: win rate on fixture history. Pass: = expected. Tool: pytest.
- [x] SEP-3.10: The tool's max drawdown for a fixture history matches the expected value.
  Probe: test: max drawdown on fixture history. Pass: = expected. Tool: pytest.
- [ ] SEP-3.11: Two independent runs on different machines produce byte-identical reports.
  Probe: test: two runs, two machines. Pass: byte-identical. Tool: diff.
- [x] SEP-3.12: Anti: a provider's track record omits a public commitment it never revealed (unrevealed commitments count as misses).
  Probe: property: provider commits long + short, reveals one. Pass: the unrevealed one scores as a miss. Tool: hypothesis.
- [x] SEP-3.13: Anti: a vote first made readable on official relays after the deadline counts, even with a valid pre-deadline anchor.
  Probe: integration: anchored vote revealed after deadline. Pass: excluded from tally. Tool: pytest + relays.
- [x] SEP-3.14: A provider exports its full signed history (events plus anchor proofs) as one bundle, and the track-record tool computes the same report from the bundle alone, with no relay, as from the relays.
  Probe: integration: export bundle; recompute offline vs from relays. Pass: byte-identical reports. Tool: pytest.
- [x] SEP-3.15: Anti: a bundle with an omitted, reordered or edited signal verifies as complete (each signal carries a sequence number and the previous signal's id, so gaps are detectable).
  Probe: property: drop / swap / edit random signals in a bundle. Pass: always flagged incomplete or invalid. Tool: hypothesis.
- [x] SEP-3.16: Anti: a signal published after the price move it claims can enter a provider's track record (signal timestamp must precede the transport's receipt time within tolerance).
  Probe: property: backdated signal. Pass: excluded. Tool: hypothesis.
- [x] SEP-3.17: A follower bot executes a received signal through Nautilus on the follower's own Binance testnet account. Evidence: `test_testnet_online.py` passed on 2026-10-19 (Binance order id returned, market buy filled, 0.00024 BTC).
  Probe: integration: follower executes on Binance spot testnet. Pass: Binance returns an order id and the order fills. Tool: pytest -m testnet (local only; needs an Ed25519 testnet key).
  Anti (SEP-3.17): a close that arrives while its entry is in flight is dropped as "nothing to close", or a stop is left resting after its position is gone. Probe: `tests/test_follower_protective.py` (backtest venue with latency; Hypothesis over random entry/close/fill/reject interleavings). Pass: the close waits, is sized to the fill, and is cancelled when the position goes flat; an entry that ends unfilled or `CLOSE_WAIT_TIMEOUT_S` drops it with the reason.
- [ ] SEP-3.18: Every signal names the bar it was decided on (`bar_open_ms` and timeframe, signed with the rest of the content); a follower rejects a signal whose bar is not the latest closed bar of that timeframe at receipt plus the tier delay, with the reason in its ledger. Lands before the public test relay (SEP-12.18), because it changes the signal format.
  Probe: test+property: signals with stale, future or wrong-timeframe bars. Pass: rejected with reason; current bar accepted. Tool: pytest + hypothesis.
- [ ] SEP-3.19: On connect a follower backfills each followed provider's stored signals and commitments it lacks (from its ledger's chain head, or from seq 1 on a fresh ledger) and records them in its ledger as history, so the ledger's chain matches what the relay holds and `sa record` over it reports no gap caused by a late join.
  Probe: integration: follower joins after seq 1..5 were published, then 6..9 arrive live. Pass: ledger holds seq 1..9, history rows flagged as backfill; no gap. Tool: pytest + sarelay.
- [ ] SEP-3.20: Anti: a backfilled signal (created before the follower's subscription) is ever executed or sent to an exchange; only signals that arrive live and pass the stale check are acted on.
  Probe: integration+property: same run; random join times. Pass: zero orders for backfilled seqs; live seqs executed as before. Tool: pytest + hypothesis.
- [x] SEP-3.21: Followers with more token power receive a signal no later than followers with less (priority ordering), measured over 100 deliveries.
  Probe: integration: delivery order vs token power. Pass: monotonic over 100 runs. Tool: pytest.
- [x] SEP-3.22: A follower's tier with a provider is computed from the token power its SA identity allocated to that provider, not from its total balance or power allocated to other providers.
  Probe: integration: 1M SA: 5% to provider A, 95% to B → tiers. Pass: T2 with A, T0 with B (default table). Tool: go test + relay.
- [x] SEP-3.23: Providers set their own tier rules.
  Probe: Holds when SEP-3.24 to SEP-3.25 all hold.
- [x] SEP-3.24: A provider's tier rule set (thresholds and delays, or private-only) is accepted only if signed via its SA identity.
  Probe: property: rule set signed by other key. Pass: rejected. Tool: go test.
- [x] SEP-3.25: The relay delivers each provider's signals according to that provider's rule set.
  Probe: integration: two providers with different rule sets. Pass: each follower tier/delay matches its provider's rules. Tool: go test + relay.
- [x] SEP-3.26: A private signal is delivered encrypted to each entitled follower (NIP-44), and an entitled follower decrypts and verifies it.
  Probe: integration: private signal to 2 entitled followers. Pass: both decrypt and verify. Tool: pytest + relay.
- [x] SEP-3.27: Anti: the relay operator or a non-entitled client can read the content of a private signal.
  Probe: integration: relay store + non-entitled client inspect private event. Pass: content unreadable. Tool: pytest + relay.
- [x] SEP-3.28: A provider can publish a timestamped commitment (hash) of a private signal and later reveal it; the track-record tool accepts a revealed signal only if its commitment predates the outcome.
  Probe: property: reveal with commitment after/before outcome. Pass: rejected/accepted. Tool: hypothesis.
- [x] SEP-3.29: Off-relay signals get the same checks as relayed ones.
  Probe: Holds when SEP-3.30 to SEP-3.31 all hold.
- [x] SEP-3.30: A valid signal received as a file or pasted text is executed by the follower bot.
  Probe: test: valid signal passed as file. Pass: executed (sandbox). Tool: pytest.
- [x] SEP-3.31: A tampered or wrongly delegated off-relay signal is rejected.
  Probe: property: tampered / wrong-delegation file signal. Pass: rejected. Tool: hypothesis.
- [x] SEP-3.32: The relay accepts a power allocation only if it is signed by the SA identity (EIP-191) and is newer than the one it replaces.
  Probe: property: allocation signed by other key / older nonce. Pass: rejected. Tool: go test.
- [x] SEP-3.33: Anti: allocations whose shares sum to more than 100% of an identity's token power are accepted.
  Probe: property: random allocations summing > 100%. Pass: rejected. Tool: go test.
- [x] SEP-3.34: Anti: the same unit of token power counts toward both a governance vote and a signals tier.
  Probe: integration: vote with power already on signals. Pass: vote weight excludes it. Tool: pytest.
- [ ] SEP-3.35: A power allocation takes effect only after a fixed delay D from its anchored publication time (D ≥ the longest voting period, provisionally 7 days), and votes count the allocation in force at the proposal's snapshot.
  Probe: property: reallocate governance→provider during an open vote. Pass: vote counts snapshot allocation; tier unchanged until D elapses. Tool: hypothesis.
- [x] SEP-3.36: The governance tally lists which official relays answered, and marks the result incomplete when any official relay is unreachable.
  Probe: integration: tally with one of 3 official relays stopped. Pass: output flags incomplete + lists relays. Tool: pytest + relays.
- [x] SEP-3.37: Anti: a vote or allocation published after a proposal's deadline changes its result.
  Probe: property: backdated post-deadline vote/allocation. Pass: result unchanged. Tool: hypothesis.
- [x] SEP-3.38: Anti: a client obtains a signal before its tier's release time by any route (live REQ, history REQ, ids, COUNT).
  Probe: integration: lower-tier probes every 20 ms before release. Pass: 0 early events. Tool: go test + relay.
- [x] SEP-3.39: Anti: a pubkey that is not a registered provider publishes a signal to the tier relay.
  Probe: integration: unregistered pubkey publishes to tier relay. Pass: rejected, 0 stored. Tool: go test + relay.
- [x] SEP-3.40: Anti: a provider shortens tier delays by sending a `timeframe` different from the one bound at registration.
  Probe: integration: publish with mismatched timeframe. Pass: rejected. Tool: go test + relay.
- [x] SEP-3.41: Pending releases survive a relay restart (each is delivered at its original release time after restart).
  Probe: integration: restart relay with pending releases. Pass: all delivered on schedule. Tool: go test + relay.
- [x] SEP-3.42: Zero token power degrades service instead of blocking it.
  Probe: Holds when SEP-3.43 to SEP-3.44 all hold.
- [x] SEP-3.43: A client with zero token power receives every signal it subscribes to.
  Probe: integration: zero-power client subscription. Pass: all signals received. Tool: pytest.
- [x] SEP-3.44: A zero-power client exceeding the documented request rate gets throttled responses, not disconnection.
  Probe: integration: zero-power client over rate. Pass: throttled, still connected. Tool: pytest.
- [ ] SEP-3.45: A signalled stop is held by the follower and never shown to the exchange (stops are never visible to the exchange, which could trade against them): Nautilus order emulation holds it and releases only a market order when the last trade price crosses it, so the exchange never receives a signalled stop price.

  Probe: test: every order the venue received while signalled stops are armed, triggered and cancelled. Pass: 0 stop-market or stop-limit orders at a signalled price, 0 UNSUPPORTED_ORDER_TYPE denials. Tool: pytest (`test_anti_the_exchange_never_receives_a_signalled_stop_price`).
