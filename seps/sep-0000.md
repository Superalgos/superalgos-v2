# SEP-0: Project scope and principles

- Status: Accepted

## Motivation

Superalgos v1 is Apache-2.0 and still has a community, but development has slowed and its code cannot be modernized in place: untyped JavaScript loaded into global namespaces by string name, strategy logic run through `eval`, REST-only exchange access, an old Electron shell, and little automated testing. The SA token's only utility has been governance since 2021, because the use it was designed for, trading signals and copy trading, was built but never proven: v1 has signal code and token-power-ordered delivery, but no time-stamped proof and no verifiable track record.

v2 does not recover or replace v1. It gathers v1's features and recreates the ones that still make sense on a new technical base.

## Vision

A self-hosted, open-source v2 where a trader signs in with the same address that holds their SA, publishes signals from a strategy on their own terms (public with tiered delays, private to chosen followers, or off-grid), and can prove their real track record from the signed, timestamped history whenever they choose to, with no server to trust. A follower's bot copies those signals from their own exchange or wallet account, on crypto CEX, DEX, stocks or forex.

A returning community member opens v2, sees a signal provider's verified six-month record computed in front of them, and follows with a click.

## Out of scope

- No new SA distribution or paid token bounties until a legal structure for the project exists.
- No custody. v2 never holds user funds or exchange keys on a server; everything executes from the user's own account.
- No porting of v1 code. v1 is frozen as legacy; ideas are harvested as specs, not code.
- No Bitcoin Factory / ML forecasting network, no P2P social-network features (posts, timelines, replies), no three-UI Social Trading app.
- No own execution engine. NautilusTrader is the backtest and live core.
- No price promises or financial-return claims in any project communication.
- No hosted SaaS in this specification; self-hosted only.

## Language

**Signal**
A signed, timestamped trading intent (instrument, side, action, size fraction, optional price/stop) published by a provider before the market outcome exists.
Avoid: alert, announcement (v1's announcements were social-bot posts, not signals).
Relationships: published by a Provider; consumed by a Follower; scored into a Track record.

**SA identity**
The EVM address holding the user's SA tokens. The root identity; never used as a hot key.
Avoid: profile, user profile (v1's GitHub-hosted node tree).
Relationships: signs Delegations to device keys.

**Token power**
The SA an identity holds across BSC and Ethereum, as a budget the holder splits between uses (governance, signals, later others). One unit serves one use at a time (as in v1's Token Power Switch).
Avoid: balance (the balance is the cap; power is what the holder allocates).
Relationships: an SA identity signs a Power allocation; a follower's tier comes from the power allocated to signals, never the raw balance.

**Power allocation**
A statement signed by the SA identity splitting its token power across uses, for example 70% signals, 30% governance.
Avoid: staking (no tokens move).

**Delegation**
A statement signed by the SA identity authorizing a device key to sign signals on its behalf, with expiry.
Avoid: signing account (v1 term).

## Principles

- Trust comes from verification, not reputation claims: anything a provider says about performance must be recomputable by anyone.
- The funds key never touches a hot device.
- Ship the smallest thing that gives SA a use; signals first, designer later. v1 stalled on "no specific objective".
- Reuse before build: Nautilus for execution, existing signing standards for identity.
- More than one maintainer must be able to understand every package.

## Constraints

- Licence Apache-2.0 for all v2 code; NautilusTrader (LGPL-3.0) used as an unmodified dependency, or modifications published under LGPL.
- Python 3.12+ for the engine side, managed by uv, Pydantic models, mypy `--strict`, Ruff. TypeScript strict + Biome for any web UI.
- Identity uses the SA-holding EVM address; login follows Sign-In with Ethereum (EIP-4361).
- Authentication is required on every network-facing endpoint from the first commit.
- No `eval` / `exec` / `new Function` of user strategy code; conditions are a typed, sandbox-free expression language.
- Coverage threshold `fail_under = 80` in the repo's own test config; pre-commit runs lint + typecheck + unit tests; CI runs the full suite.
- Self-hostable on a 4-core / 4 GB machine (the community runs Raspberry Pi / Odroid class boxes).
- The tier relay is a standalone Go service (khatru); engine and tools stay Python, UI TypeScript.
- Signals travel as Nostr events; custom tags never reuse a name a NIP already defines (a `delegation` tag crashes nostr-rs-relay via its NIP-26 handler; the SA delegation tag is `sa-delegation`).
